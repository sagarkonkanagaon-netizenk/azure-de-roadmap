📌 Phase 1 SQL + Python Foundations

Window functions · CTEs · Joins · pandas · File I/O · API calls

📚 SQL Core Concepts

  • Window functions (ROW_NUMBER, RANK, DENSE_RANK, NTILE) — Compute rankings within groups without collapsing rows. Think of them like a "sub-group calculator" that runs alongside your result set.
  • LAG / LEAD — Access previous or next row's value in the same query. Perfect for month-over-month or day-over-day comparison without a self-join.
  • CTEs (WITH clause) — Named temporary result sets you can reference multiple times. Like giving a subquery a meaningful variable name — much more readable than nested subqueries.
  • PIVOT / UNPIVOT — Rotate rows into columns (PIVOT) or columns into rows (UNPIVOT). Used for cross-tab reports and reshaping aggregations.
  • Index types: clustered vs non-clustered — Clustered index physically sorts the table data (one per table). Non-clustered creates a separate lookup structure. Think of clustered = the book's actual order; non-clustered = the index at the back.
  • ROLLUP / CUBE for subtotals and grand totals in reporting queries
  • FULL OUTER JOIN — returns all rows from both tables, NULLs where no match. Use for reconciliation reports.
  • Subqueries vs CTEs vs Window functions — when to use each

🐍 Python + pandas Concepts

  • pandas groupby + agg — Group data and apply multiple aggregation functions at once. Like SQL GROUP BY but in memory. Analogy: splitting an Excel sheet by department and summing salaries in each tab.
  • pd.merge (join types) — Combine DataFrames on key columns, same as SQL joins. The "how" parameter maps directly: left, right, inner, outer.
  • File I/O: read_parquet / to_parquet — Parquet is columnar storage — much faster for analytics than CSV. Reading a 1GB CSV vs Parquet: Parquet can be 10x faster because only needed columns are read from disk.
  • requests library + pagination — Call REST APIs, handle pagination with while loops, parse JSON response to DataFrame. Core skill for any API ingestion pipeline.
  • List comprehensions + generators — Concise loops; generators use lazy evaluation (don't load everything into memory). Analogy: generator = reading a book one page at a time vs loading the whole book.
  • Exception handling: try/except/finally for robust pipeline code
  • lambda + map/filter for quick column transformations
  • datetime module for date parsing, delta calculations, partitioning

🎯 Interview Questions — Phase 1

Q: Difference between ROW_NUMBER, RANK, DENSE_RANK?ROW_NUMBER: always unique sequential (1,2,3,4). RANK: gaps on ties (1,2,2,4). DENSE_RANK: no gaps on ties (1,2,2,3). Use DENSE_RANK when you need "top N" without gaps.
Q: When would you use a CTE vs subquery vs window function?CTE: when you reference the result multiple times or need self-referential recursion. Subquery: simple one-time inline filter. Window function: when you need row-level detail PLUS aggregate in the same row — only window functions can do this without grouping.
Q: What's the difference between WHERE and HAVING?WHERE filters rows BEFORE aggregation (can't reference aggregate functions). HAVING filters AFTER GROUP BY — it can reference COUNT(), SUM() etc. Rule: if you can put it in WHERE, do so — it's faster because it reduces rows before aggregation.
Q: How do you deduplicate a table in SQL?Use ROW_NUMBER() OVER (PARTITION BY business_key ORDER BY updated_at DESC) and keep only rn=1. This handles exact duplicates AND keeping the latest version of a record by a timestamp.
Q: What's the difference between pandas merge vs join?merge() is more flexible — works on any columns, similar to SQL JOIN. join() is a shorthand that joins on index by default. For ETL work, always use merge() with explicit left_on/right_on keys for clarity.
Q: How would you read a 10GB CSV file in Python without running out of memory?Use pandas read_csv() with chunksize parameter to process in chunks, or use polars/dask for out-of-core processing, or push the file to PySpark if already in the cloud. For production, prefer Parquet over CSV — same 10GB CSV is typically 1-2GB as Parquet.

⚡ Phase 2 Apache Spark + Databricks

Spark architecture · DataFrames · Databricks workspace · Cluster config

⚡ Spark Core Concepts

  • Driver vs Executor vs Cluster Manager — Driver is the coordinator (your main program). Executors are workers that run tasks. Cluster Manager (YARN/Kubernetes) allocates resources. Analogy: Driver = project manager, Executors = workers on the floor.
  • Lazy evaluation — Transformations (filter, select, join) build a logical plan but don't execute until an action (count, write, collect) is called. Spark uses this to optimize the full DAG before running anything — like planning a route before driving.
  • Shuffle — Data moving between executors across the network. The most expensive Spark operation. Triggered by groupBy, join, distinct, repartition. Minimize by using broadcast joins and pre-partitioning on the join key.
  • Broadcast join — For tables under ~10MB (tunable), Spark sends a copy to every executor so no shuffle is needed. Think of it as handing everyone a reference card vs passing papers around the room.
  • AQE (Adaptive Query Execution) — Spark 3.x feature that re-optimizes the query plan at runtime based on actual data statistics. Auto-coalesces small shuffle partitions and handles skew automatically.
  • RDD vs DataFrame vs Dataset — use DataFrame/Dataset always (Catalyst optimizer + Tungsten execution)
  • repartition vs coalesce — repartition triggers full shuffle (use to increase partitions or fix skew), coalesce only reduces (no shuffle)
  • Caching: cache()=MEMORY_ONLY, persist()=configurable storage level — use when DataFrame is reused 2+ times

🧱 Databricks Platform

  • Job cluster vs Interactive cluster — Job clusters auto-start and terminate with each job run (pay only for runtime). Interactive clusters stay running for dev work (expensive if left idle). Always use job clusters in production.
  • Unity Catalog — Three-level namespace: catalog.schema.table. Centralized governance across all workspaces — one place for access control, lineage, and auditing. Replaces per-workspace Hive metastore.
  • Auto Loader (cloudFiles) — Incrementally ingests new files from ADLS/S3 using file notification or directory listing. Tracks what's been processed so you don't re-ingest. Databricks' answer to file-based streaming ingestion.
  • DLT (Delta Live Tables) — Declare pipelines as SQL/Python with @dlt.table decorator. DLT manages execution order, retries, and data quality expectations automatically.
  • Databricks Secrets — Store sensitive values (connection strings, API keys) in secret scopes backed by Azure Key Vault. Reference as dbutils.secrets.get() — never hardcode secrets in notebooks.
  • %run vs dbutils.notebook.run — %run: executes inline (shares variable scope). dbutils.notebook.run: executes as a separate child notebook (isolated scope, returns single string).
  • DBFS vs Unity Catalog volumes — Use UC volumes for all new work; DBFS is legacy and being deprecated in favor of UC-governed storage.
  • Workflows: multi-task jobs with dependency graph, retry policies, alerting on failure

🎯 Interview Questions — Phase 2

Q: groupByKey vs reduceByKey in Spark?groupByKey shuffles ALL data to the reduce side — every value for a key moves across the network. reduceByKey first does local aggregation on each partition (like a combiner in MapReduce), then shuffles only the reduced results. For large datasets, reduceByKey can be 5–10x faster. Use groupBy() on DataFrames instead of RDD APIs whenever possible.
Q: What is lazy evaluation and why does it matter?Transformations like filter(), select(), join() build a logical query plan but nothing runs until you call an action (count, write, collect). Spark uses this time to apply the Catalyst optimizer — it can reorder filters, push predicates down, eliminate unnecessary columns. Without lazy evaluation, Spark can't optimize across multiple operations.
Q: How do you handle data skew in Spark?1) Broadcast join if the small table is under 10MB. 2) Salting: add a random prefix (0-N) to the skewed key on both sides, this distributes the hotkey across N partitions. 3) Enable AQE (spark.sql.adaptive.enabled=true) — Spark 3.x auto-detects skew and splits skewed partitions. 4) Repartition on a better column that distributes evenly.
Q: What's the difference between cache() and persist()?cache() is shorthand for persist(StorageLevel.MEMORY_ONLY). persist() lets you choose: MEMORY_ONLY, MEMORY_AND_DISK, DISK_ONLY, etc. Use cache() for DataFrames that fit in memory; persist(MEMORY_AND_DISK) for large DataFrames where spilling to disk is acceptable.
Q: When would you use repartition vs coalesce?repartition(N): full shuffle, can increase OR decrease partitions, use to fix data skew or balance before a write. coalesce(N): no shuffle, can only REDUCE partitions by merging existing ones — use at the end of a pipeline to write fewer output files. coalesce is always faster but can't fix skew.
Q: How does Databricks Auto Loader work?Auto Loader uses Azure Event Grid (or S3 notifications) to detect new files arriving in a landing folder — it doesn't scan the entire directory on each run. It checkpoints which files have been processed in a metadata location. This scales to millions of files without listing overhead, unlike spark.readStream.format("parquet").load() which lists everything.

🔄 Phase 3 Azure Data Factory + ADLS Gen2

Pipelines · Triggers · Linked services · Metadata-driven · Self-Hosted IR

🔄 ADF Core Concepts

  • Linked services — Connection definitions (think: JDBC connection string). One linked service per source/sink. Store credentials in Azure Key Vault, reference by secret name — never hardcode.
  • Integration Runtime (IR) — The compute that powers data movement. Azure IR = cloud-to-cloud. Self-Hosted IR = agent installed on-prem/in private VNet for on-prem data sources. SSIS IR = runs legacy SSIS packages.
  • ForEach + Lookup metadata-driven pattern — Store all table configs in an Azure SQL control table. Lookup activity reads all rows, ForEach iterates — one pipeline handles unlimited tables. Adding a new source = insert a row into the config table.
  • Watermark incremental load — Track the last-loaded timestamp per table in a control table. Each run, query source with WHERE updated_at > last_watermark. After successful copy, update the watermark. Handles any append/update pattern.
  • Triggers: Schedule vs Tumbling Window vs Event-based — Schedule: fixed cron. Tumbling Window: non-overlapping time windows, supports backfill (rerun past windows). Event-based: fires when a blob is created in ADLS — perfect for event-driven ingestion.
  • Data Flows: visual Spark-based transformations, auto-generates PySpark, runs on ADF-managed cluster
  • Error handling: each activity has success/failure/completion branches — route failures to error logging table
  • ARM template: export the whole ADF as JSON for CI/CD deployment to QA/Prod via Azure DevOps

🗄️ ADLS Gen2 Architecture

  • Hierarchical namespace (HNS) — Enables true directory semantics and directory-level ACLs (vs flat blob storage). Required for Databricks, ADF Data Flows, and any workload needing folder-level permissions. Think of it as turning blob storage into a real filesystem.
  • Medallion zone structure — landing/ (raw drop zone, 24hr retention), bronze/ (raw + audit columns, permanent), silver/ (cleaned/merged), gold/ (aggregated, BI-ready). Each layer is a separate ADLS container or folder with different ACLs.
  • Managed Identity vs Service Principal — Managed Identity: Azure-managed credential tied to a service (ADF, Databricks), no password to rotate, preferred. Service Principal: app registration with client ID/secret, you manage rotation. Always prefer Managed Identity where supported.
  • Access tiers — Hot: frequent access (default). Cool: infrequent access, 30-day min, cheaper storage + retrieval cost. Archive: offline, hours to rehydrate. Use lifecycle policies to auto-tier old Bronze data to Cool after 90 days.
  • Event Grid integration: triggers ADF pipeline on blob creation — no polling needed for event-driven pipelines
  • RBAC roles: Storage Blob Data Contributor for read/write. Storage Blob Data Reader for read-only (analysts).
  • SAS tokens: time-limited, scoped access — use for external partner data sharing only
  • Soft delete + versioning: enable on Bronze/Silver for accidental delete protection

🎯 Interview Questions — Phase 3

Q: Difference between Azure IR and Self-Hosted IR?Azure IR is fully managed, runs in Azure's network, connects to public endpoints (ADLS, Azure SQL, REST APIs). Self-Hosted IR is an agent you install on a machine inside your private network or on-prem — it reaches SQL Server, Oracle, SAP on private network without exposing them to the internet. For hybrid cloud migrations, Self-Hosted IR is essential.
Q: How do you implement incremental load in ADF?Watermark pattern: (1) store last-loaded timestamp per table in a config/control table in Azure SQL. (2) Lookup activity reads the watermark. (3) Copy Activity source query: WHERE updated_at > @LastWatermark. (4) On success, call Stored Procedure to update watermark to pipeline run time. This guarantees no data loss even if the pipeline fails midway — just re-run from last committed watermark.
Q: How do you handle schema drift in ADF pipelines?In Data Flows: enable "Allow schema drift" so new columns pass through without breaking the pipeline. Use schema drift with auto-mapping for Bronze layer where raw schema matters. For strict Silver transforms, explicitly map columns and alert on schema change via ADF monitoring. For Copy Activity, binary copy (format-agnostic) handles schema drift completely.
Q: What's the difference between Schedule trigger and Tumbling Window trigger?Schedule trigger fires at a set time — no concept of windows, can't backfill. Tumbling Window trigger defines non-overlapping time windows (e.g., daily), tracks which windows have run, supports dependency between windows (T depends on T-1), and allows you to re-trigger any past window independently for backfill. Always use Tumbling Window for time-partitioned batch loads.
Q: How do you copy a 3TB file using ADF?Use Copy Activity with binary copy format (no parsing overhead) and enable staging (stage through Azure Blob first). ADF auto-parallelizes the copy using multiple data movement units (DMUs). Set parallelCopies to match your IR capacity. For on-prem sources with Self-Hosted IR, ensure IR host has enough network bandwidth and disk buffer space.
Q: How does ADF CI/CD work?ADF uses Git integration — you commit pipeline/dataset/trigger JSON to a feature branch, merge to develop/main. On publish, ADF generates ARM template JSON to adf_publish branch. Azure DevOps pipeline detects the publish, deploys ARM template to QA environment (auto), then waits for approval gate before deploying to Production. Parametrize all environment-specific values (storage URLs, linked service names) in the ARM template parameters file.

🔥 Phase 4 PySpark + Delta Lake

MERGE INTO · SCD Type 1 & 2 · Time Travel · Z-ordering · OPTIMIZE

🔥 Delta Lake Deep Dive

  • Delta vs Parquet — Parquet is just a file format (no ACID, no updates). Delta wraps Parquet files with a transaction log that gives you ACID, time travel, schema enforcement, and concurrent reads/writes. Think of Parquet as a spreadsheet file vs Delta as a versioned database backed by spreadsheet files.
  • Transaction log (_delta_log/) — Every write (INSERT, UPDATE, DELETE, MERGE) creates a numbered JSON file (0000.json, 0001.json...). The log records which Parquet files were added/removed. Delta reads the log to reconstruct table state. After 10 log entries, it creates a checkpoint (.parquet) for fast log replay.
  • MERGE INTO (upsert) — Single atomic operation: match on key → update if match, insert if no match, optionally delete. Replaces the read-modify-write-overwrite pattern. Much safer than overwrite for Silver/Gold layers with concurrent readers.
  • OPTIMIZE + Z-ORDER — OPTIMIZE compacts many small files into larger ones (solves the "small file problem" from streaming). Z-ORDER co-locates related data in the same files by sorting on specified columns — reduces files scanned for point queries by 10–100x.
  • VACUUM — Physically deletes Parquet files no longer referenced by the transaction log. Default retention = 7 days (time travel window). Run weekly in production to reclaim storage. Never run VACUUM with retention < 7 days unless you've disabled concurrent reads.
  • Time travel: VERSION AS OF N (by version number) or TIMESTAMP AS OF '2024-01-01' — query any historical state
  • Schema evolution: mergeSchema=true allows adding new columns without rewrite; overwriteSchema=true for structural changes
  • Change Data Feed (CDF): track row-level changes (_change_type: insert/update_preimage/update_postimage/delete)

💡 Azure Synapse Analytics

  • Dedicated SQL Pool vs Serverless SQL Pool — Dedicated: provisioned DW compute (pay always, DWU-based), fast for repeated BI queries. Serverless: pay-per-query on ADLS files (no provisioning), perfect for ad-hoc exploration on Parquet/Delta files. Use Serverless for Gold layer querying, Dedicated for fixed BI workloads.
  • PolyBase / COPY INTO — Load data from ADLS into Dedicated SQL Pool. COPY INTO is the modern replacement — simpler syntax, supports more formats, better performance. Bulk load millions of rows from Parquet in minutes.
  • Distribution strategies — HASH: distribute rows by column value (use for large fact tables, join on distribution column). ROUND_ROBIN: evenly distribute (use for staging, unknown join patterns). REPLICATED: copy full table to every node (use for small dimension tables <2GB).
  • Serverless external tables — Create a view over ADLS/Delta files without moving data. Business users query via SQL without knowing it's Parquet underneath. Perfect for Gold layer serving.
  • Workload management: isolate resource classes (smallrc/mediumrc/largerc) to prevent large queries from starving smaller ones
  • Result set caching: Dedicated SQL Pool caches query results for 48 hours — repeated BI queries return in milliseconds
  • Statistics: create and auto-update statistics on join/filter columns for query plan optimization
  • Pause/Resume: Dedicated SQL Pool can be paused when not in use — saves ~100% of compute cost overnight

🎯 Interview Questions — Phase 4

Q: What is the Delta transaction log and how does it enable ACID?Every write to a Delta table generates a JSON log file in _delta_log/. Atomicity: the write either creates a new log entry or doesn't — no partial states. Isolation: optimistic concurrency control — Delta checks for conflicts at commit time and rejects conflicting writes. Reads always see a consistent snapshot based on the log at query start time. After 10 log files, a checkpoint.parquet consolidates history for fast startup.
Q: How do you handle incremental load without an updated_at column?Row hashing: compute SHA2 of all business columns as a hash string. Store it in the Delta table. On each load, compute hash of incoming rows, join to existing hash — only rows where hash differs (or is new) need MERGE. This catches any value change in any column without needing an update timestamp. SHA2(concat_ws('||', col1, col2...)) is the standard pattern.
Q: What does OPTIMIZE do and when should you run it?OPTIMIZE compacts many small Parquet files (common after streaming writes or frequent small batch writes) into larger files, typically 1GB target. Without OPTIMIZE, a query might need to open 10,000 small files — with OPTIMIZE, maybe 10 large files. Z-ORDER within OPTIMIZE also sorts data so that filter predicates skip entire files. Run after large merges or streaming ingestion jobs, or on a daily schedule.
Q: Dedicated SQL Pool vs Serverless SQL Pool in Synapse — when to use each?Dedicated: provisioned MPP compute, best for predictable BI workloads run frequently (cost is always-on by DWU). Serverless: no provisioning, pay per TB scanned, perfect for ad-hoc or infrequent queries directly on ADLS Parquet/Delta files. Use Serverless for Gold layer exploration and external tables that BI tools query — avoids double-storing data in a warehouse.
Q: What is PolyBase / COPY INTO in Synapse?COPY INTO is the modern bulk load command for Dedicated SQL Pool — loads from ADLS/Blob using Managed Identity, supports Parquet/CSV/JSON, parallelizes automatically across distributions. Replaces PolyBase external table pattern which required more setup. For millions of rows, COPY INTO completes in minutes vs hours of row-by-row INSERT.
Q: How does Delta Change Data Feed work?Enable with delta.enableChangeDataFeed=true on the table. Every DML operation logs row-level changes with _change_type column (insert, update_preimage, update_postimage, delete). Downstream pipelines can read only changed rows using spark.readStream.option("readChangeFeed", "true") — much more efficient than full table scan for incremental downstream processing.

🏗️ Phase 5 Medallion Architecture + Data Modeling

Bronze / Silver / Gold · Star Schema · Slowly Changing Dimensions · CDC

🏗️ Medallion Architecture Deep Dive

  • Bronze (Raw Layer) — Exact copy of source data, never modified after write. Add audit columns only: ingestion_timestamp, source_file_path, batch_id, pipeline_run_id. Immutable — treat Bronze as your "undo" layer. If Silver is corrupted, you re-derive it from Bronze. Partition by ingestion_date for lifecycle management.
  • Silver (Conformed Layer) — Apply business rules: dedup on natural keys, null handling, type casting (string → date, string → decimal), standardize codes (M/F → Male/Female). Apply SCD merges via Delta MERGE INTO. Partition by domain-relevant keys (region, product_category). Silver is the layer downstream systems trust.
  • Gold (Serving Layer) — Pre-aggregated, denormalized for BI performance. Star schema (fact + dims) or wide flat tables for simpler queries. Power BI DirectQuery on Gold Delta tables or Synapse Serverless external tables. Never run raw queries on Silver from BI tools — Gold is the performance layer.
  • Idempotency — Pipelines must be safe to re-run without creating duplicates. Use MERGE INTO (not append) for Silver. Use overwrite or MERGE for Gold aggregations. Always check: "what happens if this pipeline runs twice?" — answer must be: same result.
  • Error record routing — Route records failing validation to an error/ path with original data + error_reason column. Don't drop bad records — visibility into data quality issues is critical. Use DLT expectations or manual when/otherwise logic to tag and route.
  • Audit columns on Bronze: _ingestion_ts TIMESTAMP, _source_file STRING, _batch_id STRING, _pipeline_run_id STRING
  • Partition strategies: Bronze by year/month/day (for retention), Silver by business key (region, product_line), Gold by query pattern (date ranges BI filters on)

📐 Data Modeling + CDC

  • Star Schema — Central fact table (transactions, events) surrounded by dimension tables (customer, product, date, geography). Foreign keys in fact join to surrogate keys in dims. Optimized for analytical queries — Power BI can build relationships visually. Analogy: fact = every sale receipt, dimensions = the reference books (who bought, what product, which store).
  • SCD Type 2 (Slowly Changing Dimensions) — When a customer moves cities, don't overwrite — add a new row with is_current=1, valid_from=now, and expire the old row with is_current=0, valid_to=now. Historical orders still point to the customer's OLD address at time of purchase. Critical for correct historical reporting.
  • Surrogate keys vs natural keys — Surrogate: generated integer/UUID, stable, independent of source changes. Natural: business key (SSN, email) — can change, not reliable as FK. Always use surrogate keys as fact table foreign keys, keep natural key as a separate attribute column.
  • CDC (Change Data Capture) — Capture row-level changes from source DB without full table scan. SQL Server CDC: built-in feature, writes changes to _CT tables. Debezium: open source, streams changes to Kafka. Much more efficient than watermark polling for high-velocity source tables.
  • Snowflake Schema: normalize dimension tables to reduce redundancy — but adds JOIN complexity. Use only when storage is constrained or dimension updates are frequent.
  • Conformed dimensions: shared dimension tables used by multiple fact tables (e.g., dim_customer used by sales, support, billing facts). Enables cross-fact analysis.
  • Degenerate dimensions: fact attributes that act like dimensions but have no separate dim table (order_number, invoice_id) — store directly in fact table.

Q: How does CDC differ from watermark-based incremental load?Watermark polling: query source table WHERE updated_at > last_run — misses deletes, requires an update timestamp column, scans the entire source table each run. Surrogate keys are stable, compact, and join-friendly.

🔄 CI/CD for Data Pipelines

  • Git branching strategy — feature/* → develop (auto-deploy to QA) → main (approval gate → Prod). Never develop directly on main. Each feature branch is a pipeline change, not a notebook edit.
  • ADF CI/CD flow — ADF Studio is linked to Git. Developers work in feature branches. On merge to develop/main, ADF "Publish" generates an ARM template to the adf_publish branch. Azure Pipelines detects the publish and deploys the ARM template. ADF itself becomes infrastructure-as-code.

  • Variable groups in Azure DevOps: store environment-specific variables (subscription ID, resource group, ADF name) — linked to pipeline, injected at runtime
  • Pre-deployment validation: ADF ARM template has a validation mode — run it before actual deploy to catch syntax errors
  • Rollback strategy: keep previous ARM template version in artifact store, re-deploy previous version on failure

🔐 Security, Governance + Monitoring

  • Azure Key Vault integration — All secrets (connection strings, passwords, API keys) stored in Key Vault. ADF, Databricks, and Synapse access secrets via Managed Identity — no secret in code, no secret in environment variables. Key Vault access policies restrict which services can read which secrets.
  • Managed Identity vs Service Principal — Managed Identity: Azure creates and rotates credentials automatically, tied to a specific service (ADF instance). Service Principal: you create and manage client ID/secret, portable across services but you own rotation. Always prefer Managed Identity — no credential management overhead.
  • Unity Catalog governance — Three-level namespace: catalog.schema.table. GRANT/REVOKE SQL syntax for column-level and row-level access. Audit logs for all data access. Data lineage: which pipeline produced which table. Works across all Databricks workspaces in the account.
  • ADLS Gen2 ACLs — Hierarchical Namespace enables folder-level ACLs (execute on parent folders, read/write on data folders). POSIX-style: owner, group, other. Combined with RBAC roles: Storage Blob Data Reader (read-only for analysts), Storage Blob Data Contributor (read/write for pipelines).
  • Pipeline monitoring — ADF Monitor: view all pipeline runs, filter by status/date, drill into activity-level failures. Alert rules: send email/Teams notification on pipeline failure via Azure Monitor. PagerDuty integration for on-call alerting on production failures.
  • Microsoft Purview: enterprise data catalog, auto-scan ADLS/SQL/Synapse, lineage graph, sensitivity labels
  • Databricks audit logs → ADLS → Synapse: track who queried what table, when, from which cluster

🪣 Amazon S3 Deep Dive

  • Storage classes — Standard (frequent access, 11 9s durability), Standard-IA (infrequent, retrieval fee applies), One Zone-IA (single AZ, 20% cheaper), Glacier Instant/Flexible/Deep Archive (minutes to hours retrieval). Think of tiers like hotel room categories — cheaper rooms have longer check-in times.
  • Lifecycle policies — Auto-transition objects between classes based on age. E.g., move Bronze logs to IA after 30 days, Glacier after 90 days. Configure per prefix so raw data ages out cheaply while Gold tables stay in Standard.
  • Partitioning strategy — S3 is a flat key-value store but prefix structure mimics directories. Partition by s3://bucket/bronze/year=2024/month=01/day=15/ so Athena can prune partitions and read only relevant files — same as Hive partitioning.
  • S3 event notifications — Trigger Lambda, SQS, or SNS when objects land. Classic serverless ETL trigger: CSV drops to s3://landing/ → S3 event → Lambda → starts Glue job. No polling needed, sub-second latency.
  • Multipart upload — Files over 100MB should use multipart: splits into parts, uploads in parallel, reassembles. Faster and recoverable (retry only failed parts). AWS SDK does this automatically for large objects.

🔍 AWS Glue In Depth

  • Glue Crawler — Connects to S3, JDBC, or DynamoDB, samples data, infers schema, registers table in Glue Data Catalog. Like a metadata spider. Run after new data lands to keep catalog fresh. Supports incremental crawls to only scan new partitions.
  • Glue Data Catalog — Hive-compatible central metadata store. Databases and tables defined here are accessible by Athena, EMR, Redshift Spectrum, and Glue ETL jobs. Single source of truth for schema — no per-service schema management.
  • DynamicFrame vs DataFrame — DynamicFrame handles schema inconsistencies (a column might be STRING in some rows, INT in others). Use resolveChoice() to handle ambiguity. Convert to DataFrame for Spark ML or complex window functions, then back for Glue writes.
  • Job bookmarks — Glue tracks which S3 objects have been processed. On the next run, only new files are ingested — no full scan, no deduplication logic needed. Incremental processing out of the box.
  • Glue Streaming ETL — Process Kinesis or Kafka streams using micro-batches (100 seconds default). Same DynamicFrame API as batch ETL. Write directly to S3 in Parquet/Iceberg format for a serverless streaming pipeline.

⚡ Phase 2: EMR + Spark on AWS

EMR clusters · Spot instances · EMRFS · PySpark on EMR · Bootstrap actions

⚡ EMR Architecture

  • Node types — Master node: coordinates YARN, HDFS NameNode, runs job tracking. Core nodes: run YARN NodeManager AND store HDFS data (can't be spot — data loss risk). Task nodes: run only YARN tasks, no HDFS — perfect for Spot instances. Like a construction site: foreman (master), permanent crew with tools (core), temp workers (task).
  • Instance fleet vs Instance groups — Instance fleet: mix multiple instance types and On-demand + Spot in a single fleet, EMR picks cheapest available. Instance groups: fixed instance type per group, simpler but less flexible. Use instance fleet for cost optimization on Task nodes.
  • EMRFS — EMR File System: makes S3 look like HDFS to Spark/Hive. Instead of storing data locally on HDFS, jobs read/write S3 directly. Decouples compute from storage — terminate cluster after job, data persists on S3. Critical architectural pattern for ephemeral clusters.
  • Bootstrap actions — Shell scripts run on every node after cluster creation but before applications start. Use to install Python packages (pip install), configure JVM settings, or copy config files. Stored as scripts on S3 and referenced in cluster config.
  • EMR Serverless — No cluster to manage: submit jobs, EMR allocates resources, auto-scales, charges only for vCPU-seconds used. Best for variable or unpredictable workloads where a long-running cluster would sit idle. Trade-off: 1-2 minute startup latency vs immediate execution on a running cluster.

💡 Glue + Athena: Serverless Path

  • Glue vs EMR decision — Glue: fully managed, DPU-based billing, DynamicFrame handles messy schemas, built-in job bookmarks for incremental loads. EMR: full cluster control, any library, any Spark configuration, cheaper for sustained large workloads. Rule of thumb: start with Glue; switch to EMR when you need custom configs or run >4 hours/day.
  • Athena query optimization — Athena charges $5/TB scanned. Reduce cost 90% by: (1) converting CSV to Parquet (columnar, compressed), (2) partitioning by date so queries only scan relevant folders, (3) using partition projection to avoid crawling for new partitions. A query that scanned 1TB CSV now scans 80GB Parquet partitioned.

Q: How does Athena pricing work and how do you minimize cost?Athena charges $5 per TB scanned — only the bytes read from S3 count. 🏭 Phase 3: Amazon Redshift — Data Warehouse

Distribution keys · Sort keys · Spectrum · Vacuum · WLM · RA3 nodes

🏭 Redshift Architecture

  • Leader node + Compute nodes — Leader node receives queries, compiles query plan, distributes work to compute nodes. Compute nodes execute slices (sub-partitions) in parallel. RA3 nodes store data on S3 (managed storage) while compute stays elastic — you can resize compute without re-loading data. Like a general directing units: the general plans, units execute.
  • Distribution styles — KEY: hash-distribute on a column (co-locate matching rows for JOINs). EVEN: round-robin across all nodes (no key, good for large tables with no dominant join). ALL: copy entire table to every node (small dimension tables, eliminates all join shuffles). AUTO: Redshift picks for you based on table size.
  • Sort keys — COMPOUND: multi-column sort in order (best for range queries on the first column — date, region). INTERLEAVED: equal weight to all sort columns (good for ad-hoc filtering on any combination). Compound is faster for most DE workloads; use interleaved only for highly variable query patterns.
  • Redshift Spectrum — Query S3 data directly from Redshift SQL without loading it. Join Redshift internal tables with S3 external tables (via Glue Catalog) in a single query. Ideal for hot data in Redshift, cold/historical data on S3 — one query layer for both.
  • WLM (Workload Management) — Divide cluster capacity into query queues with different concurrency limits and memory allocations. Short query acceleration (SQA) routes small queries to a fast lane, preventing a 5-minute report from blocking a 2-second dashboard query.

⚡ Redshift Loading + Optimization

  • COPY command — Fastest way to load data: reads from S3 in parallel across all compute nodes. Split large files into 1 file per slice (or use auto-split manifest). COPY from CSV, JSON, Parquet, ORC. Always use COPY over INSERT for bulk loads — INSERT is single-threaded via leader node.
  • VACUUM + ANALYZE — Redshift soft-deletes rows on UPDATE/DELETE — they're marked deleted but take space. VACUUM reclaims space and re-sorts unsorted rows. ANALYZE updates table statistics so the query planner makes good decisions. Both run automatically overnight but run manually after bulk loads.
  • Materialized views — Pre-compute expensive aggregations (daily revenue by region) and store the result. Auto-refresh on a schedule or after base table changes. BI tools query the MV (sub-second) instead of the 50M-row fact table (minutes). Think of them as pre-baked answers to known questions.
  • Concurrency Scaling — When main cluster queue is full, Redshift auto-adds transient clusters to handle burst read traffic. Users experience consistent performance during peak hours without you pre-provisioning for peak. Charged per second of scaling cluster use.
  • dbt on Redshift — dbt transforms data inside Redshift using SQL models with ref() for dependency management. Incremental models use INSERT INTO ... WHERE not yet loaded. Snapshots implement SCD Type 2 automatically. Tests (not_null, unique, relationships) validate data quality in CI/CD.

🎯 Redshift Interview Questions

Q: What distribution key should you choose?Choose the column most used in JOINs between large tables — this co-locates matching rows on the same compute node, eliminating cross-node data movement (the most expensive operation). Avoid high-skew columns (e.g., status with 90% rows = 'active'). If no clear join key or table is small, use ALL distribution for dimension tables and EVEN for large fact tables with varied query patterns.
Q: What does VACUUM do in Redshift?Redshift uses soft deletes — UPDATE and DELETE mark rows as deleted but don't physically remove them, wasting space. VACUUM DELETE reclaims that space. VACUUM SORT re-sorts rows that were loaded out of sort-key order (bulk loads don't re-sort automatically). Auto-vacuum handles this overnight but after a large load, manual VACUUM FULL ensures immediate optimization for the next query.
Q: Compound vs Interleaved sort keys?Compound sort key is ordered — the first column is the primary sort (like a phone book sorted by last name then first name). Best for queries filtering on the first column and range scans. Interleaved sort key gives equal weight to all columns — better for unpredictable ad-hoc queries that filter on any combination of columns. In practice, compound is 95% of use cases — interleaved has higher VACUUM cost and rarely outperforms compound significantly.
Q: How does WLM work and why configure it?WLM queues carve up cluster memory and concurrency. Without WLM, a heavy ETL job running COPY + transforms can consume all memory and time out dashboard queries. Separate queues for: ETL (high memory, low concurrency), BI reports (medium), ad-hoc (low memory, high concurrency). Short Query Acceleration (SQA) automatically extracts queries under ~6 seconds and runs them in a fast lane without waiting in the main queue.
Q: When would you use Redshift Serverless vs provisioned?Serverless: auto-scaling, pay per RPU-second, no cluster management, zero when idle — ideal for unpredictable workloads, dev/test, or BI tools with variable query load. Provisioned: predictable performance, reserved node pricing (significant discount), better for sustained workloads with consistent throughput needs. Serverless is more expensive per query but cheaper overall if the cluster would sit idle for hours.

🌊 Phase 4: Kinesis — Real-Time Streaming

Data Streams · Firehose · Analytics · Lambda consumer · Shard management

🌊 Kinesis Family Deep Dive

  • Kinesis Data Streams (KDS) — Real-time, ordered, replay-capable stream. Data stays 24h (up to 7 days). Multiple consumers can read the same stream independently. 1 shard = 1MB/s write + 2MB/s read. Partition key hashes to a shard — pick a high-cardinality key to avoid hot shards. Think of each shard as a lane on a highway.
  • Kinesis Firehose — Fully managed delivery pipeline: reads from KDS or direct PUT, buffers (60s or 1MB default), then delivers to S3, Redshift, OpenSearch, or HTTP endpoint. No custom consumer code needed. Add Lambda transform for lightweight enrichment (parse JSON, mask PII) before delivery. Best for S3 landing zone pipelines.
  • Kinesis Data Analytics (KDA) — Run Apache Flink on your streams. Windowed aggregations, joins between streams, pattern detection with CEP (complex event processing). Flink checkpoints to S3 for fault tolerance — a failed job restarts from last checkpoint. Use for real-time aggregations, anomaly detection, or complex stateful processing.
  • Enhanced fan-out — Each registered consumer gets dedicated 2MB/s throughput per shard rather than sharing the 2MB/s pool with other consumers. Up to 5 consumers per shard without throttling. Critical when multiple downstream services (Lambda, KDA, custom KCL app) all read the same stream.
  • MSK (Managed Kafka) — Fully managed Apache Kafka for teams that need Kafka semantics, large ecosystems (Kafka Connect, Schema Registry), or are migrating from on-prem Kafka. KDS is simpler (fewer configs), MSK is more powerful (replication factor control, topic compaction, consumer groups with lag metrics). MSK Serverless for variable throughput.

💡 Streaming Architecture Patterns

  • Firehose → S3 → Glue Crawler → Athena — The simplest serverless streaming pipeline: events → Firehose (buffer 60s) → S3 Parquet → Glue Crawler (hourly) → Athena queries. No servers, sub-minute latency to S3, $5/TB query cost. Add Lambda transform in Firehose for enrichment.
  • KDS → Lambda → DynamoDB — Event-driven real-time pattern: Lambda triggered by KDS batch (100 records or 5 minutes). Lambda enriches and writes to DynamoDB for millisecond lookups. Lambda scales automatically with shard count. Use for real-time leaderboards, user state updates, fraud signals.
  • KDS → KDA (Flink) → S3 + DynamoDB — Dual-sink pattern: KDA computes rolling aggregates to DynamoDB (real-time serving) and writes raw + windowed results to S3 (analytics). Flink exactly-once semantics with two-phase commit ensures no duplicates even on failure.
  • MSK → Glue Streaming → Iceberg on S3 — Kafka producers → MSK → Glue Streaming ETL job reads Kafka topic → transforms and writes Apache Iceberg on S3 → Athena queries with MERGE support. Full streaming lakehouse with ACID on S3.
  • Dead letter + replay — Kinesis retains data up to 7 days. Failed consumers (Lambda DLQ, KCL app errors) can replay from a specific sequence number or timestamp. Always implement DLQ for Lambda KDS triggers — failed batches go to SQS DLQ for inspection and manual replay.

Q: Kinesis vs SQS — when to use each?Kinesis Data Streams: ordered within a shard, data retained 24h-7 days for replay, multiple independent consumers read simultaneously, designed for high-throughput streaming analytics. Q: What is Kinesis Firehose and how is it different from KDS?Firehose is a managed delivery service — you don't write consumer code. It buffers records (time or size threshold) and delivers to S3, Redshift, OpenSearch, or HTTP. KDS is a raw stream — you write consumers (Lambda, KDA, KCL app). Q: Kinesis Data Analytics vs Lambda for stream processing?Lambda: event-driven, simple record-by-record or mini-batch processing, 15-minute max execution, no built-in windowing. KDA/Flink: full stateful stream processor with windowed aggregations (tumbling, sliding, session), joins between streams, exactly-once semantics, indefinitely running. Use Lambda for simple transformations and routing; use KDA for complex analytics, aggregations over time, or pattern detection requiring state.

Kinesis: simpler setup, native AWS IAM auth, no Kafka expertise needed, better integration with Lambda/Firehose. Choose MSK when you need Kafka-specific features or have on-prem Kafka to migrate; choose Kinesis for greenfield AWS-native streaming pipelines.

🏛️ Lake Formation + Security

  • Lake Formation centralized permissions — Instead of IAM policies + S3 bucket policies + Glue Catalog permissions (three places), Lake Formation is a single permission layer. Grant/revoke table, column, or row access from one console. Underlying S3 permissions are managed automatically by LF.
  • Column-level security — Grant SELECT on specific columns only. Analysts can query a customer table but column SSN is excluded from their grants — Athena/Glue queries automatically strip the column from results. No views needed — enforced at the catalog level.
  • Row-level security (RLS) — Row filters restrict which rows a principal can see. Define a filter condition (region = 'APAC') and apply it to an IAM role or group. APAC analysts only see APAC rows even when querying the full table — enforcement happens at Glue/Athena scan time.

When a new table is tagged sensitivity=PII, all IAM roles with PII grants get access automatically — scales to hundreds of tables without individual grants.
  • Cross-account data sharing — Share a Glue Catalog database with another AWS account via Lake Formation RAM integration. Recipient account can query your S3 data through Athena/Redshift Spectrum without you copying data. Permissions controlled by the producer account.

🎯 Lakehouse + Certification Interview Questions

Q: What is a data lakehouse and how does AWS implement it?A data lakehouse combines cheap object storage (lake) with ACID transactions and SQL analytics (warehouse). AWS implements it with: S3 as the storage layer, Iceberg or LF governed tables for ACID, Glue Catalog as the unified metastore, and multiple compute engines (Athena for serverless SQL, Redshift Spectrum for warehouse queries, EMR for Spark) all reading the same S3 data. You get 90% of warehouse performance at 10% of the cost for analytical workloads.
Q: Apache Iceberg vs Delta Lake vs Apache Hudi?All three add ACID transactions to S3/HDFS Parquet files. Iceberg: broadest engine support (Athena, Spark, Flink, Hive, Trino), immutable snapshots for time travel, partition evolution without rewriting data — AWS's preferred open table format. Delta Lake: tightest Databricks/Spark integration, DBT native support, strong on Azure. Hudi: designed for incremental/streaming workloads, record-level indexing for fastest upserts — popular on Amazon EMR for CDC. On AWS, use Iceberg unless you have a specific Delta Lake requirement.
Q: How does Iceberg time travel work?Iceberg maintains a snapshot log — every INSERT, UPDATE, DELETE, or MERGE creates a new snapshot with a timestamp and snapshot ID. Old data files aren't deleted until you run EXPIRE SNAPSHOTS. Query old snapshots with SELECT ... FOR SYSTEM_TIME AS OF '2024-01-01' or FOR VERSION AS OF snapshot_id. Time travel is invaluable for: debugging when a bad load occurred, reconstructing data as-of-report-date for audit, and A/B comparing pipeline outputs.
Q: What AWS services are covered in the AWS Data Engineer Associate exam?Core exam domains: Data Ingestion (Kinesis, DMS, Snow family, DataSync), Storage and Catalog (S3, Glue Catalog, Lake Formation), Processing (Glue ETL, EMR, Lambda), Serving (Redshift, Athena, QuickSight), Orchestration (Step Functions, MWAA, EventBridge), Security (IAM, KMS, Secrets Manager, VPC), and Monitoring (CloudWatch, CloudTrail). The exam emphasizes choosing the RIGHT AWS service for the scenario — not just knowing what each service does, but knowing when to use Kinesis vs SQS vs MSK.

🎯 BigQuery Interview Questions

Q: Partitioning vs Clustering in BigQuery?Partitioning: divides table into separate storage segments — a query with WHERE date BETWEEN filters to relevant segments, eliminating irrelevant partitions from the scan entirely (reduces bytes billed). Clustering: sorts rows within each partition by up to 4 columns — a query filtering by customer_id on a clustered table skips data blocks that don't match, reducing bytes read further. Best practice: partition by date first, cluster by the most-filtered dimension columns. Together they can reduce a full-table scan by 95%+.
Q: On-demand vs flat-rate (slots) pricing?On-demand: $5/TB scanned, no commitment — cost directly tied to bytes read. Optimize by partitioning, clustering, and Parquet format. Flat-rate: purchase reserved slot capacity (100-slot increments), unlimited queries, billed per slot-hour. Break-even is roughly 500TB/month scanned. Use on-demand for variable workloads and development; flat-rate for production BI with consistent daily volume. Editions (Standard, Enterprise, Enterprise Plus) replace the old flat-rate model with hourly or annual commitments.
Q: How do you optimize a slow BigQuery query?Step 1: Check INFORMATION_SCHEMA.JOBS for bytes processed and slot time. Step 2: ensure partition pruning is happening (WHERE on partition column). Step 3: add clustering on filter/join columns. Step 4: avoid SELECT * — list only needed columns. Step 5: replace correlated subqueries with JOINs or window functions. Step 6: use APPROX_COUNT_DISTINCT instead of COUNT(DISTINCT) for approximate cardinality. BigQuery's query plan in the console shows stage-by-stage slot usage and bytes shuffled.
Q: What is BI Engine and when would you use it?BI Engine is an in-memory analysis service that caches table data for sub-second query response. Reserve capacity (1GB to 250GB per project), and queries against cached tables skip the full scan — results returned from memory in milliseconds. Best for BI dashboard tools (Looker, Data Studio) with repetitive queries against the same tables. BI Engine accelerates compatible queries automatically without code changes. Not suitable for ad-hoc exploratory queries that vary widely in what they filter.
Q: What is BigQuery ML?BigQuery ML lets you train, evaluate, and serve ML models using SQL. Supported models: linear/logistic regression, k-means clustering, matrix factorization, XGBoost, TensorFlow, and AutoML. CREATE MODEL trains on a BigQuery table; ML.PREDICT scores new data. The advantage: data stays in BigQuery — no export to a separate ML platform for common use cases. Best for data engineers who need to build simple predictive models (churn score, product recommendation) without a dedicated ML infrastructure.
Q: How does BigQuery handle streaming inserts?BigQuery Storage Write API (recommended) or legacy tabledata.insertAll API (streaming inserts). Storage Write API: committed, buffered, and pending stream modes. Committed mode guarantees exactly-once — a row written with the same offset is deduplicated. Buffered mode provides hourly snapshots for near-real-time with lower latency than batch. Legacy streaming inserts: immediately queryable but more expensive ($0.01/200MB) and no exactly-once guarantee without client-side dedup. For Dataflow → BigQuery streaming, use Storage Write API with exactly-once semantics.

⚙️ Phase 3: Dataproc — Managed Hadoop/Spark

⚙️ Dataproc Architecture

  • Ephemeral cluster pattern — Create cluster, run Spark job, delete cluster — all in one Cloud Composer DAG or gcloud command. No idle cluster cost. 90-second startup means per-job clusters are practical. Data stays on GCS permanently; cluster is just transient compute. Cost: pay only for the minutes the cluster runs.
  • Preemptible VMs for workers — Preemptible VMs are 60-80% cheaper but can be reclaimed with 30 seconds notice. Safe for Dataproc Task/worker nodes because Spark restarts failed tasks. Never use preemptible for the master node. Mix: 2 standard core VMs + 10 preemptible workers for a 60%+ cost reduction on large batch jobs.
  • GCS as HDFS — Dataproc uses GCS as the storage backend via the Cloud Storage Connector. spark.read("gs://...") works the same as HDFS read. GCS is infinite (no HDFS capacity planning), durable (11 9s), and shared across clusters (no data locality optimization but network is fast enough). HDFS still exists on cluster nodes for temp shuffle data.
  • Dataproc Serverless — Submit a Spark batch job without creating a cluster. Google manages resource provisioning, autoscaling, and teardown. Pay per vCPU-second. 90-second startup replaced by ~3-minute job start. Best for infrequent, variable-size Spark jobs where managing cluster lifecycle adds overhead.
  • BigQuery Connector — Read from BigQuery into Spark DataFrame with spark.read.format("bigquery").option("table", "project.dataset.table"). Write results back. Dataproc can process data that originates in BigQuery or write Spark results to BigQuery for BI. Avoids exporting to GCS as intermediate step.

💡 Dataproc vs Dataflow Decision

  • When to choose Dataproc — Existing Spark/Hadoop code you want to lift-and-shift to GCP. Complex PySpark transformations with custom libraries. Jobs requiring Spark SQL, Hive, or machine learning (Spark MLlib). Teams with strong Spark expertise. Large-scale Spark workloads where you need full cluster tuning (executor memory, shuffle partitions).
  • When to choose Dataflow — New pipelines that need both batch and streaming with one codebase. Fully serverless (no cluster management). Built-in connectors to Pub/Sub, BigQuery, GCS, Bigtable. Simpler operational model — no cluster config, no tuning shuffle partitions. Recommended for GCP-native greenfield projects.
  • Dataproc Metastore — Managed Hive Metastore on GCP: stores table schemas, partition metadata, and storage locations. Compatible with Hive, Spark, and Presto/Trino. Shared across clusters — multiple Dataproc clusters or Dataflow jobs reference the same metadata. Integrates with Dataplex for governance.
  • Initialization actions — Shell scripts run on all nodes after cluster creation. Install pip packages, configure Spark properties, download ML models. Scripts stored on GCS and referenced at cluster creation. Baked into cluster templates or Composer DAG cluster config so every job cluster starts identically configured.
  • Autoscaling — Dataproc autoscales worker count based on YARN pending memory. Set min/max workers; Dataproc scales up when jobs wait for resources and down when workers sit idle. Works best with preemptible workers as the autoscaling layer — standard workers as the stable base.

🔄 DAG Design Patterns

  • GCS → Dataproc → BigQuery ETL DAG — GCSObjectExistenceSensor (wait for file) → DataprocCreateCluster → DataprocSubmitJob (PySpark) → DataprocDeleteCluster → BigQueryInsertJobOperator (merge/upsert). Error branch on cluster creation failure → SNS/PagerDuty alert. Most common GCP batch ETL pattern.
  • Dynamic task mapping (Airflow 2.3+) — expand() creates tasks dynamically from a list at runtime. Example: get list of active tables from BigQuery → map over the list → one task per table. Replaces manual ForEach or nested DAG patterns. Limits: up to 1024 mapped tasks per DAG run.
  • TaskGroups — Group related tasks visually in the Airflow UI and apply shared retry/timeout settings. Useful for representing Bronze → Silver → Gold layers as collapsible groups. No execution difference from individual tasks — purely organizational.
  • Trigger rules — ALL_SUCCESS (default), ALL_FAILED, ONE_SUCCESS, ALL_DONE, NONE_FAILED. Use ALL_DONE to run cleanup tasks whether upstream succeeded or failed. Use ONE_SUCCESS for parallel branches where any completion triggers the next step. Trigger rules enable complex conditional DAG flows.
  • Backfill — airflow dags backfill -s 2024-01-01 -e 2024-01-31 my_dag_id: re-runs all DAG runs for the date range. Useful after a data fix (reprocess last 30 days) or for initial historical load. Composer runs these as regular DAG runs — they appear in the UI and respect task dependencies.

🏛️ BigQuery Advanced Features

  • Authorized views — Share a subset of a table with users who don't have access to the underlying table. Create a view that filters rows or excludes columns, then "authorize" it in the source dataset settings. Users query the view but can't query the base table. No data copying, no row-level policy needed for simple slices.
  • Row-level access policies — CREATE ROW ACCESS POLICY on a table with a filter expression (region = SESSION_USER()). Each query is automatically filtered — the user sees only their authorized rows even on SELECT *. Unlike authorized views, RLS is enforced at the table level so it applies regardless of which view or query is used to access the table.
  • Column-level security with policy tags — Tag a BigQuery column with a policy tag (PII/SSN). Users without the policy tag IAM permission get an error querying that column. Managed in Data Catalog taxonomy. Enforced across all access methods — Looker, direct BigQuery, Dataflow reads all respect column-level security.
  • Materialized views in BigQuery — Pre-compute aggregations (daily revenue by region) as a materialized view. BigQuery increments the MV automatically as base table data changes — only new data since last refresh is re-computed, not the whole table. BI Engine accelerates MV queries further. For known recurring query patterns, MVs can reduce cost by 80%+.
  • BigQuery Reservations + Commitments — Purchase slot capacity (100-slot increments) with 1-minute, monthly, or annual commitment. Assignments route specific projects or folders to a reservation. Mix: baseline slots on annual commitment (70% discount), burst slots on-demand for peak. INFORMATION_SCHEMA.JOBS_BY_RESERVATION monitors per-reservation utilization.

Project 4 · Delta Lake CDC Pipeline

Problem: A financial services firm needs to maintain a customer master in Delta Lake that reflects the source SQL Server truth in near-real-time (sub-hour lag) including deletes — which watermark polling cannot capture. Regulatory requirements demand a full audit trail of every change (who changed what, when), making SCD Type 2 mandatory for key dimension tables.

Architecture: SQL Server CDC → ADF (reads _CT change tables) → ADLS Bronze (CDC rows) → Databricks (apply CDC as MERGE/DELETE) → Delta Silver with full change history → Synapse external table

  • Enable SQL Server CDC on source database: EXEC sys.sp_cdc_enable_db; EXEC sys.sp_cdc_enable_table for each tracked table
  • ADF pipeline reads CDC change tables (cdc.dbo_customers_CT) — each row has __$operation (1=delete, 2=insert, 3=before-update, 4=after-update)
  • Watermark on __$start_lsn (log sequence number) rather than timestamp — LSN is monotonically increasing and more reliable than datetime for CDC
  • ADF Copy Activity lands CDC rows to ADLS Bronze: /bronze/cdc/customers/yyyy/MM/dd/ with all CDC metadata columns preserved
  • Databricks CDC processor: read Bronze CDC Parquet, parse __$operation into action (INSERT/UPDATE/DELETE), filter to keep only operation 2 and 4 (insert + after-update), deduplicate by primary key keeping latest LSN
  • Apply INSERTs and UPDATEs via Delta MERGE INTO Silver customer table (SCD Type 1 for most columns)
  • Handle DELETEs: soft-delete pattern — set is_deleted=true and deleted_ts=current_timestamp via MERGE whenMatchedUpdate rather than physical delete (preserves foreign key integrity)
  • SCD Type 2 for critical tracked columns (email, credit_limit, account_status): expire old record (is_current=0, valid_to=now), insert new record (is_current=1, valid_from=now)
  • CDC audit table: log every __$operation with old values (operation=3, before-update) and new values (operation=4) for regulatory audit trail
  • Delta Change Data Feed on Silver: downstream Gold table reads only changed rows using readChangeFeed=true — no full scan needed
  • Test scenarios: verify delete propagation, verify SCD Type 2 history retention, verify idempotency (re-process same CDC batch), verify late-arriving CDC rows (out-of-order LSN)
  • Schedule via ADF Tumbling Window trigger every 30 minutes for near-real-time lag

⚡ PySpark — Core Concepts
  • Lazy Evaluation: Transformations build a logical plan; actions execute it. Enables Catalyst optimizer to reorder, push down, and optimize before running.
  • groupByKey vs reduceByKey: reduceByKey = combines locally per partition before shuffle (map-side reduce). groupByKey = sends all to reducer. Always use reduceByKey.
  • repartition vs coalesce: repartition = full shuffle, increase or decrease. coalesce = no shuffle, decrease only. Use coalesce before write to reduce output files.
  • Broadcast join: Copies small table (<10MB default) to all executors. Eliminates shuffle on large table. Use broadcast() hint.
  • Jobs/Stages/Tasks: 1 Action = 1 Job. Wide transform = new Stage boundary. Tasks = partition count per stage.
  • AQE: Adaptive Query Execution — dynamically adjusts plan at runtime: coalesces small partitions, changes join strategy, handles skew. Default in Databricks.
  • Incremental without updated_at: SHA2 row hash → merge on key + hash mismatch. No hash change = no update.
  • Data Skew: Salting — add random prefix to skewed key, repartition, process, aggregate. AQE handles automatically in Databricks.
🗄️ SQL — Coding & Concepts
  • nth highest salary: DENSE_RANK() OVER (ORDER BY salary DESC) = n, or OFFSET (n-1) ROWS FETCH NEXT 1 ROW ONLY
  • Top 3 per dept: DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) <= 3
  • Cumulative sum: SUM(salary) OVER (PARTITION BY dept ORDER BY hire_date ROWS UNBOUNDED PRECEDING)
  • More than manager: Self-join employees e1 JOIN employees e2 ON e1.manager_id = e2.emp_id WHERE e1.salary > e2.salary
  • TRUNCATE vs DELETE: TRUNCATE = DDL, no WHERE, no rollback, resets identity, faster. DELETE = DML, supports WHERE, can rollback.
  • Union vs Union All: Union removes dupes (slower sort). Union All keeps all rows (faster). Use Union All unless dedup required.
  • Star vs Snowflake: Star = denormalized dims, faster queries. Snowflake = normalized dims, less storage, more joins. Use Star for BI.
  • Gaps in sequence: LAG() to find where current_id - prev_id > 1
🔷 Azure Data Factory — Patterns
  • Incremental load: Lookup watermark → Copy WHERE updated_at > watermark → Update watermark table with new max
  • Metadata-driven pipeline: Config table with source/target mapping → Lookup activity reads it → ForEach loops → Copy with dynamic parameters
  • IR types: Azure IR (cloud-to-cloud), Self-Hosted IR (on-prem/private network), Azure-SSIS IR (SSIS package execution)
  • 3TB from on-prem: Self-Hosted IR + binary copy + staging blob + parallel copy settings + schedule off-peak
  • Error handling: On Failure path → error folder + retry policy + skip incompatible rows + Logic App email alert
  • Schema drift: Enable "Allow schema drift" in Data Flow source + dynamic column mappings using patterns
  • Key Vault: Create AKV Linked Service → reference secret using @{linkedService().secretName} in linked service definition
🏭 Databricks — Platform & Unity Catalog
  • Job vs Interactive cluster: Interactive = long-running, shared, for dev. Job cluster = spun up per job, terminates after, cheaper, for production.
  • Unity Catalog: 3-level: catalog.schema.table. Cross-workspace data sharing. Row/column security. Automated lineage. Centralized governance.
  • %run vs dbutils.notebook.run(): %run = inline in same session (shares vars). dbutils.notebook.run() = separate session, returns string, supports timeout.
  • Delta Log: _delta_log/ = JSON per transaction + checkpoint every 10 commits. Enables ACID, time travel, schema history.
  • cache() vs persist(): cache() = MEMORY_ONLY. persist() = specify level: MEMORY_AND_DISK for large data.
  • Autoscaling: Min/max workers based on pending tasks. ~2min to scale up — don't use for time-critical streaming.
  • DLT (Delta Live Tables): Declarative pipelines with @dlt.table decorator. Auto-handles dependencies, errors, monitoring.
💾 Delta Lake — Advanced Patterns
  • Delta vs Parquet: Parquet = columnar format only. Delta = file format + transaction log + ACID + time travel + schema enforcement + MERGE + streaming.
  • MERGE INTO: Atomic upsert — insert new, update changed, optionally delete. Single atomic operation. Uses matched/not-matched conditions.
  • Time Travel: SELECT * FROM table VERSION AS OF 5 or TIMESTAMP AS OF '2024-01-01'. Used for auditing and debugging.
  • Z-Ordering: Co-locates related data in same files. OPTIMIZE table ZORDER BY (column). Enables file skipping on high-cardinality filter columns.
  • OPTIMIZE: Compacts many small files → ~1GB files. Improves read performance. Run periodically, not after every write.
  • VACUUM: Physically deletes unreferenced files. Default 7-day retention. Running removes time travel ability beyond retention.
  • SCD Type 2: On change: update old record (set end_date=today, is_current=False) → insert new record (start_date=today, is_current=True)
🐍 Python — Coding Questions
  • Palindrome: s == s[::-1]
  • Word count: from collections import Counter; Counter(s.split())
  • Fibonacci: generator: a,b=0,1; while True: yield a; a,b=b,a+b
  • Split name: df['first']=df['name'].str.split().str[0]; df['last']=df['name'].str.split().str[-1]
  • Duplicates in list: [x for x,c in Counter(lst).items() if c>1]
  • Replace vowels: import re; re.sub('[aeiouAEIOU]', ' ', s)
  • Merge dicts: {**d1, **d2} or d1|d2 (Python 3.9+)
  • List vs Tuple vs Set: List=ordered mutable. Tuple=ordered immutable. Set=unordered no dupes.
🗄️ Data Modeling — Concepts & Patterns
  • Star vs Snowflake Schema: Star = denormalized dims (one join to fact). Snowflake = normalized dims (multiple joins). Star wins for BI query speed; Snowflake saves storage and avoids update anomalies.
  • Fact vs Dimension table: Fact = measurable events (sales, clicks, transactions) with FKs + metrics. Dimension = descriptive context (customer, product, date). Fact is tall; Dim is wide.
  • Grain of a fact table: The lowest level of detail one row represents. Always define grain first — e.g., "one row per order line item per day". Determines what can and cannot be measured.
  • SCD Type 1 vs 2 vs 3: Type 1 = overwrite (no history). Type 2 = new row per change (full history, valid_from/to, is_current). Type 3 = previous_value column (only tracks 1 change). Type 2 is standard for most DW dimensions.
  • Junk dimension: Groups low-cardinality flags/indicators (is_promo, is_online, channel_code) into a single dimension to avoid multiple tiny FK columns in the fact table.
  • Degenerate dimension: A dim attribute that lives in the fact table with no separate dim table — e.g., invoice_number, order_id. No lookup needed.
  • Conformed dimension: A dimension shared across multiple fact tables (e.g., Date dim used in Sales fact AND Inventory fact). Enables drill-across reports.
  • Data Vault vs Kimball: Data Vault = Hub (business key) + Link (relationships) + Satellite (attributes with history). Audit-friendly, parallelizable loads. Kimball = Star schema, BI-optimized. Many orgs use Data Vault in raw/staging and Kimball in gold/serving layer.
🧑‍💼 Manager Round — Behavioural & Leadership
  • "Tell me about yourself" structure: 60 seconds max — Current role + years → one key achievement → why you're looking → why this company. Rehearse it. Never read from memory.
  • Conflict with a team member: STAR format — Situation (what was the disagreement), Task (your role), Action (you listened, found common ground, escalated if needed), Result (project succeeded, relationship intact). Never badmouth the person.
  • Handling tight deadlines: Prioritize by impact, communicate blockers early, break into MVPs, ask for help without ego. Show you managed expectations — not that you quietly burnt out.
  • "What's your biggest failure?": Choose a real one. Show what you learned and what you changed. Avoid disguised positives ("I work too hard"). Interviewers see through them.
  • Ownership vs Collaboration: Show both — "I drove X end-to-end" AND "I pulled in Y team for Z expertise." Senior DE roles want someone who leads AND works across teams.
  • Handling ambiguous requirements: Ask clarifying questions, document assumptions, deliver a v1 with explicit caveats, get feedback early. Shows engineering maturity.
  • Why do you want to leave?: Focus forward — bigger scope, multi-cloud exposure, leadership opportunity — not current problems. Keep it positive and honest.
  • Salary negotiation: Give a range, not a point. Research market first. Never anchor below your current CTC. Counter with value: "Given my experience with X and impact on Y, I was expecting Z."
  • Questions to ask the interviewer: "What does a successful first 90 days look like?" / "What's the biggest data challenge the team is solving this year?" / "How is the data team structured?" Shows you're evaluating them too.
  • 3-minute project narration: Problem → My role → Tech choices (and WHY) → Challenges faced → Business impact (numbers if possible) → What I'd do differently. Practice this for all 3 major projects.
